# 言栖

言栖使用普通 QQ 账号记录群聊，昵称“小栖”。它保存收到的消息和附件，用 AI 整理技术讨论、排错过程、方案比较和头脑风暴。可以自动整理，也可以按群成员的要求回看历史、记录新讨论或发送已有纪要。

管理台用于查看原文、编辑纪要、处理失败任务和修改配置。项目通过 Docker 运行，数据保存在仓库的 `data/` 目录。

## 启动

安装 Docker 和 Docker Compose 后运行：

```sh
docker compose up -d --build
docker compose logs yanqi
```

打开 [言栖管理台](http://127.0.0.1:3210)，填写日志中的安装码并设置管理密码。然后完成以下配置：

1. 打开 [NapCat 管理页](http://127.0.0.1:6099/webui)。页面登录 Token 可用 `docker compose logs napcat` 查看。进入后扫码或输入 QQ 密码登录。
2. 在 NapCat 的网络配置中启用正向 WebSocket 服务端，监听 `0.0.0.0:3001`，设置 Token，消息格式选 `array`，打开“上报自身消息”。
3. 在言栖“设置”中填写机器人 QQ 号和相同的 OneBot Token。WebSocket 地址默认为 `ws://napcat:3001`。在“模型服务”中填写主模型的服务地址、API Key 和模型名称。
4. 保存设置，在“群与成员”中同步群列表，开启所需群的“保存消息”。按需开启“自动整理”，并授权其他成员与小栖交互。
5. 填齐配置后机器人自动运行，之后也默认随服务启动。顶部按钮可以暂停或启动 AI 处理；自动启动开关在设置中。

NapCat 管理页的登录 Token 与 OneBot Token 用途不同，分别用于登录页面和连接 WebSocket。QQ 登录、验证及切换账号都在 NapCat 中完成；切换后也要更新言栖的机器人 QQ 号。登录状态保存在挂载目录中。参见 [NapCat 配置说明](https://github.com/NapNeko/NapCat-Docker#配置与更新)。

模型、权限和机器人参数都在管理台中设置，无需创建 `.env`。API Key 和 OneBot Token 在登录后的设置页直接显示，可以修改或清空。保存时先写入数据库，再应用到机器人；当前对话会中断，后台整理会使用新配置继续。

Compose 在宿主机所有网络接口上开放言栖的 `3210` 和 NapCat 的 `6099` 端口。远程访问时，将上述地址中的 `127.0.0.1` 换成服务器地址，并在言栖设置中填写可访问的 NapCat 管理页地址。WebSocket 只在容器网络内使用，容器的 `/app/data` 挂载到仓库的 `data/`。通过反向代理访问时，需保留浏览器访问的 `Host`，并正确设置 `X-Forwarded-Proto`，供同源校验和 HTTPS 会话 Cookie 使用。

## 在群里使用

全局管理员、本群授权成员、群主和群管理员可以向小栖发出请求。其他成员的消息照常保存并参与整理，但不会触发对话或 🐳 回应。

保存消息不需要 @、关键词或 AI 通过判断。已启用记录的群中，每条收到的消息先入库，再决定是否调用 AI。

可以直接 @ 小栖，也可以说“小栖，帮我记一下”。未 @ 时，直接叫它、向它提问、要求回复或执行记录事务，都会经过请求识别模型交给主模型处理。例如“bot 在吗”“bot 看到这句话回复我一下”“小栖～”应当得到简短回应。群友之间聊天或只是谈到它时保持安静。自动发现值得整理的讨论是另一项功能，可按群开关。

回答小栖的追问时无需再次 @，请求识别模型会结合当前消息和聊天上下文判断是否继续对话。

| 想做什么       | 示例                                           |
| -------------- | ---------------------------------------------- |
| 整理刚才的讨论 | 小栖，把刚才的部署方案整理一下                 |
| 从全部历史选材 | 从全部讨论中找出对小栖的优化建议，另建一份文档 |
| 指定时间或成员 | 整理今天的讨论；从某人第一次发言到现在都记下来 |
| 连续记录       | 开始记录，把前面的部署讨论也包含进去；结束记录 |
| 查找或发送纪要 | 找一下之前讨论数据库的记录；把这份纪要发出来   |
| 补全已有纪要   | 把这份纪要补全为全部历史里的相关建议           |
| 查看进度或用量 | 那张图识别完了吗；今天 AI 用了多少 token       |
| 处理失败任务   | 重试这张图；重试本群失败任务                   |

这些是自然语言示例，不是固定命令。模型会结合引用、回复关系和上下文确定范围，必要时向前读取聊天。已有足够信息时，不要求用户提供标题、话题 ID 或逐条挑选消息。

“全部”指截至请求发出时已在本地保存的全部历史，不能包含机器人接入前未收到的聊天。“今天”按北京时间的自然日计算。“从某人第一次发言开始”包含此后所有人的讨论。跨话题整理会逐段读取指定范围，保留相关建议、理由、约束和分歧，不默认缩成最近五分钟。

连续记录从开始请求之后算起，到结束请求之前为止，不受 AI 处理耗时影响。开始或结束时都可以要求并入更早的内容。只回顾已有讨论时会直接安排整理，不必先开启连续记录。

原消息上的 🐳 表示小栖已接受请求，不代表回复或纪要已完成。获准成员 @ 小栖时直接标记，未 @ 的请求在识别通过后标记。仅保存消息或等待识别不会加表情。表情 ID 可在“运行参数”中修改，留空关闭；发送表情失败会记日志，不影响后续处理。

## 查看和管理记录

群里可以让小栖发送已有纪要，也可以在管理台查看：

| 页面     | 操作                                                           |
| -------- | -------------------------------------------------------------- |
| 概览     | 查看各群的消息、纪要和待处理任务                               |
| 纪要     | 搜索、阅读、查看原文和历史版本，编辑、导出、重新整理或发送到群 |
| 原始消息 | 搜索聊天，查看撤回标记、附件及识别结果，下载附件或重试解析     |
| 群与成员 | 同步群列表与成员，启用消息保存和自动整理，授权交互成员         |
| 后台任务 | 查看进度、错误和发送状态，重试失败任务或取消排队任务           |
| 记忆     | 查看、添加、修改和删除成员的偏好与约定                         |
| 模型用量 | 按日期、服务商、模型和用途查看调用次数及 token 用量            |
| 运行日志 | 筛选、暂停刷新和导出最近 1,000 条日志                          |
| 设置     | 配置连接、模型、人设、权限、额度和超时                         |

“原始消息”和纪要的“完整原文”使用聊天气泡展示，按日期分隔，保留昵称、QQ 号、发送时间、引用和撤回标记。图片可点击放大，附件可下载，识别内容可展开查看。纪要原文对应所选版本，也可下载为 Markdown。

聊天记录和成员列表显示 QQ 头像，首次显示时下载并缓存在本地，同一个 QQ 号在不同群中共用缓存。头像下载失败时显示昵称首字，机器人显示图标。成员更换头像后，可在“设置 → 存储与清理”点击“刷新头像缓存”，下次显示时重新获取。

顶部按钮控制 AI 处理。暂停后取消进行中的 AI 请求，仍保存已启用群的新消息和撤回标记，原文可在管理台查看。重新启动会继续后台整理和附件解析，不执行暂停期间的旧对话指令。消息保存需要言栖服务运行且 NapCat 在线；整个服务关闭期间的聊天不会自动补回。

管理台新建或重新整理的纪要只保存在本地，点击“发送到群”后才发送。编辑纪要会保存为新版本。删除纪要前需暂停 AI；删除会移除全部版本和导出文件，保留原始群消息。待发送消息也需暂停 AI 后才能取消，已发送消息不能在管理台撤回。

在群里要求修改、补全或重做已有纪要时，小栖通过 `edit_record(action=update)` 给同一篇文档创建下一版，保留旧版；即使没有新消息也能重新整理。`read(action=versions)` 可列出历史版本，读取正文或发送时可用 `revision` 指定第几版。初次整理用 `record`；针对已有纪要，只有要求独立文档或另存一份时才新建，从第 1 版开始。

关闭某个群的“自动整理”后，仍会保存消息并处理有权限成员的请求；关闭“保存消息”后，小栖不再处理该群的新消息。

## 纪要内容与保存位置

纪要先写核心问题、结论或未解决的阻碍，再展开方案、理由、条件和分歧。同一问题的补充放在一起，合并重复赞同，保留独立信息、技术细节和必要的发言人。逐字聊天另存为原文，正文不机械复述每条消息。

| 路径                                             | 内容                                            |
| ------------------------------------------------ | ----------------------------------------------- |
| `data/management.sqlite`                         | 管理台配置、管理账号、登录会话和头像缓存        |
| `data/yanqi.sqlite`                              | 群消息、话题简介、纪要、记忆、任务和模型用量    |
| `data/assets/`                                   | 按内容去重后的附件文件                          |
| `data/groups/<群号>/topics/<话题 ID>/v<版本号>/` | 每版纪要的 `note.md` 和完整原文 `transcript.md` |
| `data/napcat/`                                   | NapCat 配置和 QQ 登录数据                       |

整理开始时先导出原文，再逐批写入纪要草稿。完成前文件顶部标有“草稿”，完成后保存整版纪要到数据库。处理中断时，已写出的草稿仍可查看。原文使用北京时间，按“昵称（QQ 号）：内容”排列，保留多行正文、代码和附件链接。跨主题选材时，原文保留完整检索范围，正文只整理相关内容。

本地纪要使用 Markdown。发送到 QQ 前，[Marked](https://marked.js.org/) 渲染器会把标题转为【标题】、强调转为「重点」，并处理列表、引用和表格，保留代码和外部链接。长内容按行分段，过长的单行再拆开。原文链接只留在本地，不发 `transcript.md` 链接，也不自动附加管理台提示。

更新纪要时复用已整理的段落，只重新处理新增原文或受撤回、附件识别结果、整理要求变化影响的部分。长记录分批提取和合并，草稿随进度保存。合并超出模型限制时会拆小批次；单段仍超限时保留已生成的正文，不从头重跑整份记录。

## 存储与清理

在“设置 → 存储与清理”设置保留天数，默认 30 天，填 0 关闭清理。服务启动后及每小时执行一次，也可以手动清理。暂停 AI 不会停止保存消息或清理历史。

仅清理超过保留期、且没有被使用的消息及附件。纪要当前范围、历史版本、记忆和待处理请求引用的消息会保留。群里有任务执行或等待处理的对话时暂缓清理；附件下载时也会暂缓。清理同时移除指向已删除消息和附件的任务。

消息的群号、QQ 消息号、发送者、昵称、时间、回复关系、撤回状态和可搜索正文仍保存在数据库列中。完整消息片段使用 `[类型, 数据]` 数组表示，经 Brotli 无损压缩后存为 SQLite BLOB。表情、@、引用、附件和未知消息类型的数据都保留，不用 AI 摘要代替原文。压缩和解压只在存储层进行，搜索仍直接查询正文和时间索引。

新下载的附件按内容哈希共用文件，图片、音视频不重复压缩。已有附件路径继续可用，最后一条引用删除时才删除文件。SQLite 会复用空闲页，数据库文件不一定随每次清理立即缩小。

## 模型与回复

主模型负责理解请求、使用工具、识别讨论、整理纪要和生成群回复。视觉、语音和请求识别服务可分别填写地址、API Key 和模型名称，使用不同服务商。

视觉服务需支持 OpenAI 兼容的图片输入，语音服务需支持 `/audio/transcriptions`。未启用时仍保存附件原件，之后配置模型可按需解析。主模型可等待指定附件任务完成后再回答；任务信息包含处理对象、进度、错误和重试时间。

群回复的[系统提示词](packages/bot/src/agent/prompts/common.ts)已吸收 speak-plainly 的写作要求。简单交流简短回应，具体问题保留必要的数据、原因、条件和步骤，没有固定字数上限。主对话通过 `reply` 结束：`text` 为文字时向群里答复，为 `null` 时明确不发消息。没有成功调用 `reply` 就继续下一轮，最多调用模型 8 轮，不再把普通文本当作任务完成。模型请求报错、取消或输出截断时按错误结束。内部分析和计划不会转发。发送已有纪要直接读取数据库，避免让模型重复输出全文。

[默认人设](packages/bot/src/agent/prompts/persona.ts)参考诀的认真和洛茜的俏皮，通过称呼、用词和对话示例表现自然的群友口吻。示例用于学习语气，不是固定回复；简单招呼轻快，具体问题保留必要细节。可在设置中修改，只影响群回复和保存通知的措辞，不能改变事实、权限、工具选择、记录范围或发送决定。仓库中的 [speak-plainly 原文](skills/speak-plainly/SKILL.md)仅供参考，运行时不读取或调用。

刚安排整理时只能确认已开始。文件和数据库都保存成功后，再按用户要求和当前群聊决定发送全文、简短通知或不发消息。保存通知包含纪要标题；补整理旧讨论默认不打扰群聊。同一次发送请求不重复播报状态，用户再次明确要求时可以重发。

使用 DeepSeek 官方接口时，未 @ 消息的请求识别、分段整理、按主题选材和合并纪要启用 `high` 思考；普通对话、话题识别、保存通知和图片识别关闭思考。Clef 等独立决策服务不受此设置影响，其他服务商沿用其服务设置。

- 思考请求默认最多输出 32,768 token，超时 5 分钟，对应 `AI_THINKING_MAX_OUTPUT_TOKENS` 和 `AI_THINKING_TIMEOUT_MS`。
- 普通请求默认最多输出 8,192 token，超时 2 分钟，对应 `AI_MAX_OUTPUT_TOKENS` 和 `AI_TIMEOUT_MS`。
- 输出上限包含思考内容、正文和工具参数，与 QQ 回复长度不同。达到每日调用上限后，后台任务延后重试，消息继续保存。
- `AI_INPUT_CHARS` 控制原文分段和检索结果的大小，不代表模型的上下文容量，也不会缩小每轮请求的输出额度。

请求日志中的 `max_tokens` 来自实际发送的参数。响应日志保留服务返回的 `finish_reason` 和响应 ID，便于区分长度限制、连接中断和正常结束。

结构化输出先按标准 JSON 解析，失败时用 [jsonrepair](https://github.com/josdejong/jsonrepair) 修复常见语法错误，再由 TypeBox 校验。缺少字段、类型错误或输出被截断仍按失败处理。

### 请求识别服务

在“设置 → 请求识别”中选择主模型、Clef、OpenAI、Vercel 或 JEV。独立服务调用失败时会记录错误，不回退到主模型。只有选择“主模型”才使用 `AI_MODEL` 识别请求。

模型逐条判断消息是否需要小栖回应或处理，结合称呼、语义、回复关系和上下文确定说话对象，不按关键词匹配。结果为 `process` 时交给主模型，`ignore` 时结束；置信度只记日志，不设额外拦截阈值。群友讨论如何优化记录、介绍权限、转述指令或互相闲聊不触发；直接叫它、向它提问或要求答复时，即使没有记录任务也要回应。主模型按当前意图选择工具，只有实际记录要求才操作纪要，记忆也只在用户要求记住或更正时保存。

未 @ 的新消息从第一条起收集一秒，再等待后台轮询处理。同批消息共用上下文，暂停自动整理或话题识别失败不会阻塞这个入口。关闭“识别未 @ 的请求”后，@、引用回复和回答追问仍有效。失败或重启后不重新处理旧消息。

[Cloudflare Clef](https://developers.cloudflare.com/workers-ai/models/clef/) 配置：

| 字段                 | 填写内容                                                                              |
| -------------------- | ------------------------------------------------------------------------------------- |
| 完整接口地址（POST） | `https://api.cloudflare.com/client/v4/accounts/你的账户ID/ai/run/@cf/cloudflare/clef` |
| 模型名称             | `clef`                                                                                |
| API Key              | 有 Workers AI 权限的 API Token，不加 `Bearer` 前缀                                    |

在 Cloudflare 控制台 **Workers AI → Use REST API** 获取 Account ID 并创建 API Token。权限说明见[官方 REST API 文档](https://developers.cloudflare.com/workers-ai/get-started/rest-api/)。

OpenAI 和 Vercel 填服务地址（Base URL）、密钥和模型名称。JEV 填完整 POST 接口地址。协议实现位于 `packages/bot/src/agent/decisions/`。

## 排查问题

先在“后台任务”查看具体任务的进度和错误。图片没识别时，查看对应附件任务；文件已保存不代表内容已识别。可以重试指定任务，也可以让小栖等待结果后回答。对话请求不能从头重试，需在群里重新说明还要做什么。

“模型用量”只汇总服务商已上报的数据，未上报的调用单独计数，不按零费用处理。输入、输出和缓存用量按服务商、模型、用途和配置项保存，配置项用于区分凭据，不保存密钥本身。实际费用以服务商账单为准。

在“设置 → 运行参数”中选择日志等级和详情长度。查看容器日志：

```sh
docker compose --ansi always logs -f --no-log-prefix yanqi
```

日志使用 Koishi logger，包含毫秒时间、模块名和等级。镜像固定启用颜色，时区为 `Asia/Shanghai`。

`info` 记录任务、模型请求、工具调用和发送结果。任务 ID、群号、消息 ID 和模型调用编号可用于追踪同一次请求。模型请求会显示思考档位、输出上限和超时，返回时分别显示正文、思考和工具参数的长度，以及 token 用量和耗时。

`debug` 还记录参数、结果片段和错误堆栈，可能含聊天正文。每段默认最多 4,000 字符，可通过 `LOG_DETAIL_CHARS` 修改。日志会隐藏 AI 密钥和 OneBot Token，不输出完整请求头或图片 base64。管理台日志列表在服务重启后清空，历史日志仍可通过容器查看。

## 代码结构

根目录是 Nuxt + Naive UI 管理台，`app/` 放页面，`server/` 放接口和服务初始化。页面不使用 SSR。Nitro 启动时创建一个 `Yanqi` 实例，通过 `start()`、`stop()` 和 `configure()` 管理机器人。

管理台和机器人统一使用 Kysely 和 Node 内置的 `node:sqlite`。服务端打开、关闭数据库，并将业务数据库传给机器人。配置仍存放在 `management.sqlite`，群消息和纪要仍存放在 `yanqi.sqlite`，沿用现有表和压缩消息格式。Koishi 负责 QQ 事件与连接，不再管理数据库。

以下路径相对于 `packages/bot/src`：

| 模块                                          | 职责                                                       |
| --------------------------------------------- | ---------------------------------------------------------- |
| `secretary.ts`                                | 接收、保存消息，安排讨论识别                               |
| `onebot/`                                     | 转换和发送 QQ 消息、添加表情回应                           |
| `tasks/worker.ts`                             | 执行任务、控制并发、处理重试                               |
| `agent/requests.ts`                           | 准备当前请求的上下文和工具                                 |
| `agent/tools/`                                | 9 个工具入口，只处理当前群数据，执行前检查请求是否撤回     |
| `agent/decisions/`                            | 主模型、OpenAI/Vercel、JEV 和 Clef 的请求识别实现          |
| `agent/dialog.ts`、`recording.ts`、`media.ts` | 对话、讨论整理与发布、媒体理解，共用 `runtime.ts` 调用模型 |
| `recording/`                                  | 选择原文、分段整理、保存纪要、决定是否发送                 |
| `storage/`                                    | 读写消息、话题、纪要、附件、记忆、用量和任务               |

`read` 按需读取资料，`record` 新建纪要，`edit_record` 修改或发送已有纪要，`follow` 开始或结束连续记录。已知完整范围时直接安排整理；需要回看上下文时，使用分页结果确定消息起止 ID。记录工具返回任务 ID，`task` 可查看、等待或重试。

对话最多并发四个，同一群内同一成员的请求依次处理。附件最多并发两个，话题识别和纪要任务各自依次执行；单份纪要最多同时整理两段。对话、请求识别、话题识别、整理和附件处理分别运行，文字与纪要发送也使用独立队列。被等待的任务优先执行，等待时间不计入模型请求超时。

主模型在同一次调用中生成带人设的答复，`reply` 等待 QQ 发送结果后结束对话。保存后的发布判断也在一次调用中决定发全文、通知或不发消息，并生成所需通知。发送队列只发送已有内容，不调用模型改写。

外部依赖版本统一写在根目录 `pnpm-workspace.yaml` 的 `catalog` 中，各包用 `catalog:` 引用，本地机器人库用 `workspace:*`。

## 开发

使用根目录 `packageManager` 指定的 pnpm，以及 `engines` 支持的 Node.js 版本：

```sh
npx get-pnpm
pnpm install
pnpm lint:fix
pnpm check
pnpm build
```

`pnpm build` 生成 Nuxt 服务。运行时使用 `docker compose up -d --build`，由管理台启停机器人。
