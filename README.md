# 言栖

言栖是用普通 QQ 账号工作的群聊书记，昵称“小栖”。它把收到的群消息保存到本地，用 AI 整理技术讨论、排错、方案比较和头脑风暴。

只有 `ADMIN_IDS` 中的成员、当前群的群主和群管理员可以与小栖交互。权限在消息入口处理，@、引用回复、追问后的回答和未 @ 的记录请求都遵守这条规则。其他成员的消息和附件照常保存、参与整理，但不会触发对话或 🐳 回应。进入 Agent 的请求统一视为已授权，工具不再区分管理员和普通成员。

平时，小栖按批次判断哪些讨论或独立观点值得记录。也可以直接说“小栖，帮我记一下”，不必 @；入口模型只识别记录请求，不主动接闲聊。识别后交给主 Agent，由它结合引用和上下文确定记录范围，再安排整理。@ 它时，还可以查询或发送已有纪要。

话题简介、完整纪要和原文保存在本地 SQLite。更新纪要时复用已整理的段落，新增原文只生成新增部分；撤回或附件识别结果变化时，更新受影响的段落。查询时 AI 使用简介，发送全文时直接从数据库读取。

每版纪要也会导出到 `DATA_DIR/groups/<群号>/topics/<话题 ID>/v<版本号>/`。开始整理时先写出 `transcript.md`，随后逐批更新 `note.md`；尚未完成时文件顶部标为草稿，完成后去掉标记并将整版纪要保存到数据库。整理中断时，已写出的草稿仍可查看。原始讨论按北京时间排列，使用“昵称（QQ 号）：内容”的格式，保留多行正文、代码和附件链接。

在群里 @ 小栖说“找一下之前讨论数据库的记录”，可以查找已有纪要；说“把这份纪要发出来”，会从数据库读取全文发送。连续记录从开始请求之后算起，到结束请求之前为止，不受 AI 处理耗时影响。开始或结束时也可以要求把更早的内容并入同一份记录，例如“把刚才的部署讨论也包含进去，继续记录”。

讨论前不必先开启记录。说“从某人第一次发言到现在都记下来”，会从本群已保存的该成员首次发言起，读取随后所有人的讨论，不局限于近期上下文。

小栖追问后，同一位成员的下一句会继续交给 AI，不需要再次 @；引用小栖的回复也可以接着聊。是否属于上一轮对话仍由 AI 结合上下文判断。

收到请求后会先给原消息加 🐳，表示“收到了”，不代表纪要已经保存。使用 Koishi 的表情回应接口；`ACK_EMOJI_ID` 可改为 QQ 支持的表情 ID，设为空可关闭。回应失败会记日志，不影响处理请求。

也可以说“从全部讨论中找出对小栖的优化建议，另建一份文档”。AI 会把检索范围和整理要求交给后台，逐段读取截至这次请求本地保存的全部群成员消息，按语义保留相关建议、理由和分歧，不受近期上下文或单个话题限制。可以指定某一天、起止日期或多个话题；“今天”按北京时间的自然日计算。纪要只整理相关内容，附带的 `transcript.md` 保留检索范围内的完整原文，便于查看上下文。机器人接入前未保存的聊天不在范围内。

纪要按问题和方案归纳：合并重复赞同，保留不同观点、理由、条件和分歧。逐字聊天放在 `transcript.md`，纪要正文不逐条复述聊天。

长记录先分批提取，再合并批次之间相关的观点。提取和合并都按输入预算分批，草稿随提取进度写入；已有段落会复用，原文或选材要求变化后才重新提取。

对话、记录请求识别、话题识别、纪要整理和附件处理各自运行。普通回复与纪要发送也使用独立队列。主 Agent 直接写出带人设的答复，调用 `reply` 发送后结束，不再额外调用模型改写或收尾。发送队列只负责发送，不调用 AI。

AI 只有调用 `reply` 才能向群里说话；会话中的普通文本和分析不会转发。直接与它交流时可以回应，但不主动延长闲聊。选范围、调用工具、决定是否发送等内部过程不应播报。

问“今天 AI 用了多少 token”可查本群按提供商、配置项、模型和用途汇总的用量。每轮调用及缓存用量保存在本地 `usage` 表，配置项名称用于区分 key，不保存 key 本身。没有上报用量的调用单独计数，不能视为零费用；金额以提供商账单为准。

排查问题时设 `LOG_LEVEL=debug`，查看 `docker compose logs -f --no-log-prefix yanqi`。任务、群号、请求消息编号和 AI 调用编号会关联模型请求、工具调用与结果；每轮还会记录用量行号、提供商、输入字符数和耗时。`LOG_DETAIL_CHARS` 控制参数、结果和异常片段的长度，默认 4000；配置中的密钥会隐藏。

`AI_DETECT_MODEL` 用于记录请求识别和自动话题识别，可选便宜的小模型。两者分别执行；前者只决定是否交给主 Agent，后者判断哪些原文值得自动归档。@ 请求直接交给主 Agent。用户请求的记录范围由主 Agent 确定，不由入口模型猜测。

`AUTO_REPLY=true` 时，获准交互成员的新消息收集一秒后进入记录请求识别队列，实际启动还受 `WORK_INTERVAL_MS` 轮询和排队影响。模型按语义判断用户是否在请机器人记录、整理、转写或调整记录，不匹配固定称呼或关键词；寒暄、只叫名字、成员之间的对话不会因此唤起主 Agent。记录范围尚不清楚也会交给主 Agent 处理。暂停自动归档、话题识别失败都不会阻塞这个入口；失败或重启后不重放旧请求。设为 `false` 可关闭未 @ 请求的识别，@、引用和追问后的回答继续有效。沿用 `AUTO_REPLY` 配置名，已有 `.env` 不需要改动。

主 Agent 收到“帮我记一下”后，先判断用户指的是哪段讨论。近期上下文不足时，调用 `read(action=context)` 向前翻聊天，找到讨论开头和结束处，再用消息起止 ID 指定完整范围；长消息的完整原文可用 `read(action=history)` 读取。不会把当前看到的片段当作全部讨论，也不默认缩成最近五分钟。范围确定后，后台处理原文、附件转写和摘要；只要求整理已有讨论时立即安排 `record`，只有需要持续记录后续发言时才使用 `follow`。

`read` 按需读取原文、纪要或记录状态；`record` 创建新文档，`edit_record` 更新、发送或暂缓已有纪要，`follow` 开始或结束连续记录。标题可由 AI 拟定，不需要用户提供话题 ID 或逐条挑选消息。后台整理仍受每日 AI 调用预算限制，额度不足时延后重试。

“把这份纪要补全为全部历史里的相关建议”会更新原文档的范围和选材要求，重新整理受影响的内容，不必另建文档。

群回复的[系统提示词](src/agent/prompts/common.ts)已吸收 speak-plainly 的写作原则：按问题和上下文决定篇幅，没有固定字数、句数或条数上限。简单交流简短接话，具体问题保留所需的数据、原因、条件和步骤；删除重复、无关状态、内部过程说明和套话收尾。详略由模型按语义判断，没有关键词或场景路由。原始 [skill 文件](skills/speak-plainly/SKILL.md)仅留作参考，运行时不读取或调用。这些要求优先于人设，人设只调整表达，不改变事实、权限或工具决策。纪要正文仍通过 `edit_record(action=send)` 完整发送。

[小栖的人设](PERSONA.md)参考《明日方舟：终末地》官方发布的[诀](https://www.sina.cn/news/detail/5319448434838801.html)与[洛茜](https://www.bilibili.com/opus/1183932040381202436)介绍，改写为做事认真利落、待人亲近俏皮的美少女书记。保留诀的认真，融入洛茜的朝气与自信，减少冷淡和疏离；不用傲娇、嘴硬或固定口头禅表现个性。这是小栖自己的风格，不复刻游戏身份或台词，也不因此增加主动闲聊。人设文件在启动时读取，修改后需重启言栖。

对话最多同时处理四个请求，同一群内同一成员的请求仍依次处理；附件最多同时处理两个。话题识别和纪要任务各自顺序执行，一份纪要中互不依赖的段落最多同时整理两段。`reply` 等待 QQ 发送结果后返回，发送不必等 Agent 完全结束。

每个附件都带有处理任务 ID。对话 Agent 可以通过 `task` 查看、等待或重试指定任务，等待后读取最新识别结果。被等待的任务优先领取；等待不会占用模型请求的超时时间。之前只下载、未识别的图片和语音，会在配置对应模型后按需解析。状态查询会返回具体任务类型、对象、进度、错误及重试时间。

刚安排整理时只能说“已开始”，不能说“记好了”。文件和数据库均保存成功后，AI 结合原讨论的时间、当前群聊和用户要求，选择发纪要、简短通知或安静保存。后台补整理旧话题默认不打扰群聊，不再把“不发全文”自动变成“发送保存通知”。需要通知时保留纪要标题。用户主动要求发送时仍可重发。同一次请求还问了其他问题，才另外调用 `reply` 回答。人设只影响发言语气，不能改变这些完成状态。

可以 @ 小栖询问记录和任务状态。后台整理、识别、附件和发送失败时，管理员可以要求“重试本群失败任务”。旧的 @ 请求不会从头重跑，避免重复开始、结束记录或改变范围；对话失败后，直接说明还要继续做什么。暂停自动整理后，仍会保存群消息并处理 @ 请求；自动任务等恢复后继续。

## 代码结构

入口在 `app.ts`：注册 Koishi 消息、撤回事件和定时轮询，交给 `Secretary`。没有额外的机器人插件或自定义生命周期。

| 模块                                          | 职责                                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------------- |
| `secretary.ts`                                | 收消息、保存、回应 🐳，安排待处理的讨论                                             |
| `onebot/`                                     | QQ 消息转换、发送和表情回应；`outbox.ts` 只消费发送队列                             |
| `tasks/worker.ts`                             | 领取任务、控制并发、执行和处理失败重试                                              |
| `agent/requests.ts`                           | 准备当前请求的上下文和工具                                                          |
| `agent/tools/`                                | 9 个工具入口；统一检查请求是否撤回，各工具只处理当前群的数据                        |
| `agent/dialog.ts`、`recording.ts`、`media.ts` | 分别处理对话与措辞、讨论整理、媒体理解；共用 `runtime.ts` 的模型调用                |
| `recording/`                                  | 选原文、分段整理、写入纪要和决定是否发布                                            |
| `storage/`                                    | 按消息、话题、记录、纪要、附件、记忆、用量和队列存取 SQLite；`Store` 只组装这些对象 |

对话调用记录工具后拿到具体任务 ID，可以用 `task` 等待结果。后台整理先写草稿，再保存完整版本，最后决定发布。发送全文直接读数据库。后台保存通知通过 `AI_REPLY_MODEL` 调整措辞，普通对话由 `AI_INTENT_MODEL` 直接生成。数据库和 Markdown 的格式没有改变。

## 用 Docker 启动

安装 Docker 和 Docker Compose。已有 `.env` 就直接使用；没有时，先复制配置示例：

```sh
cp .env.example .env
```

填写机器人 QQ 号 `BOT_QQ`、记录群 `GROUP_IDS`、`ONEBOT_TOKEN`，以及 `AI_MODEL`。`ADMIN_IDS` 用逗号分隔可额外交互的 QQ 号；留空时只允许各群群主和群管理员交互。每个模型配置都使用 `BASE_URL,API_KEY,MODEL`，逗号之间不加空格，可以分别使用不同服务：

```dotenv
AI_MODEL=https://text.example/v1,text-api-key,text-model
AI_DETECT_MODEL=
AI_INTENT_MODEL=
AI_REPLY_MODEL=https://reply.example/v1,reply-api-key,reply-model
AI_VISION_MODEL=https://vision.example/v1,vision-api-key,vision-model
AI_AUDIO_MODEL=https://audio.example/v1,audio-api-key,audio-model
```

`AI_DETECT_MODEL`、`AI_INTENT_MODEL` 和 `AI_REPLY_MODEL` 留空时使用 `AI_MODEL` 的整套配置；`AI_VISION_MODEL` 和 `AI_AUDIO_MODEL` 留空时不解析对应附件。图片服务需要支持图片输入，音频服务需要支持 OpenAI 兼容的 `/audio/transcriptions`。原来的 `AI_BASE_URL`、`AI_API_KEY` 已合并进各模型配置，独立决策服务仍使用 `DECISION_*` 配置。

然后在项目目录运行：

```sh
docker compose up -d --build
```

Compose 一起启动 NapCat 和言栖。言栖读取本地 `.env`，通过 `ws://napcat:3001` 连接 NapCat；两边共用 `ONEBOT_TOKEN`，消息格式自动设为 `array`。容器配置不需要改动 `.env` 中用于本地运行的 `ONEBOT_URL`。

需要密码自动登录时，在 `.env` 中填写 `NAPCAT_QUICK_PASSWORD_MD5`，值为 QQ 密码的 32 位 MD5。NapCat 会先使用已保存的登录状态，首次登录或快速登录失败时再尝试密码登录。QQ 若要求验证码或新设备验证，需要在 WebUI 中完成。参数和登录流程见 [NapCat 登录实现](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-shell/base.ts)。

需要扫码或完成登录验证时，打开 [NapCat WebUI](http://127.0.0.1:6099/webui)，从日志中获取 WebUI 登录 token。扫码时使用 `BOT_QQ` 对应的 QQ。WebUI token 与 `ONEBOT_TOKEN` 是两个不同的凭据。登录方式见 [NapCat 官方说明](https://github.com/NapNeko/NapCat-Docker#登录)。

```sh
docker compose logs -f napcat
```

QQ 登录后，言栖会自动连接。查看言栖日志：

```sh
docker compose --ansi always logs -f --no-log-prefix yanqi
```

默认 `LOG_LEVEL=info` 会记录任务入队、开始、完成或重试，AI 模型与轮次、返回状态和 token 用量，工具调用，以及群消息发送结果。日志按毫秒时间、模块名、等级和正文排列，模块名按列对齐；AI 日志同时标明所属任务或发送编号，并行处理时仍能追到对应请求。整理进度、草稿路径和最终保存位置也会写入日志。

沿用 Koishi 自带的 logger。容器没有 TTY 时，底层库默认关闭颜色，所以 Compose 显示的服务名前缀可能有颜色，应用日志却没有。Compose 配置已通过 `FORCE_COLOR=2` 开启应用颜色，并默认使用北京时间（`TZ=Asia/Shanghai`）。修改后需要重新创建言栖容器；旧日志不会补上颜色。在 `.env` 中设 `FORCE_COLOR=0` 可关闭应用颜色。上面的 `--ansi always` 控制 Compose 的 ANSI 输出，`--no-log-prefix` 则去掉重复的服务名前缀。直接在终端运行时，logger 自动判断颜色支持。

需要查看 AI 输入和返回片段、工具参数与结果、异常堆栈时，在 `.env` 中设置 `LOG_LEVEL=debug`，然后更新容器：

```sh
docker compose up -d --build yanqi
docker compose --ansi always logs -f --no-log-prefix yanqi
```

Debug 日志的输入、返回内容和工具详情另起一行，长对象会换行缩进。这些详情可能包含聊天内容，每条默认最多显示 4000 个字符，可通过 `LOG_DETAIL_CHARS` 调整，并隐藏配置中的 AI 密钥、决策服务密钥和 OneBot token。不会打印请求头、完整配置或图片的 base64 数据。开启 debug 只调整言栖的日志，不开启适配器的底层报文日志。
