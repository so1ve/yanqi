# 言栖

言栖是用普通 QQ 账号工作的群聊书记，昵称“小栖”。它把收到的群消息保存到本地，用 AI 整理技术讨论、排错、方案比较和头脑风暴。

全局管理员、本群授权名单、当前群的群主和群管理员可以与小栖交互。权限在消息入口处理，@、引用回复、追问后的回答和未 @ 的记录请求都遵守这条规则。其他成员的消息和附件照常保存、参与整理，但不会触发对话或 🐳 回应。进入 Agent 的请求统一视为已授权，工具不再区分管理员和普通成员。

平时，小栖按批次判断哪些讨论或独立观点值得记录。也可以直接说“小栖，帮我记一下”，不必 @；入口模型只识别记录请求，不主动接闲聊。识别后交给主 Agent，由它结合引用和上下文确定记录范围，再安排整理。@ 它时，还可以查询或发送已有纪要。

话题简介、完整纪要和原文保存在本地 SQLite。更新纪要时复用已整理的段落，新增原文只生成新增部分；撤回或附件识别结果变化时，更新受影响的段落。查询时 AI 使用简介，发送全文时直接从数据库读取。

每版纪要也会导出到 `DATA_DIR/groups/<群号>/topics/<话题 ID>/v<版本号>/`。开始整理时先写出 `transcript.md`，随后逐批更新 `note.md`；尚未完成时文件顶部标为草稿，完成后去掉标记并将整版纪要保存到数据库。整理中断时，已写出的草稿仍可查看。原始讨论按北京时间排列，使用“昵称（QQ 号）：内容”的格式，保留多行正文、代码和附件链接。

在群里 @ 小栖说“找一下之前讨论数据库的记录”，可以查找已有纪要；说“把这份纪要发出来”，会从数据库读取全文发送。连续记录从开始请求之后算起，到结束请求之前为止，不受 AI 处理耗时影响。开始或结束时也可以要求把更早的内容并入同一份记录，例如“把刚才的部署讨论也包含进去，继续记录”。

讨论前不必先开启记录。说“从某人第一次发言到现在都记下来”，会从本群已保存的该成员首次发言起，读取随后所有人的讨论，不局限于近期上下文。

小栖追问后，同一位成员的下一句会继续交给 AI，不需要再次 @；引用小栖的回复也可以接着聊。是否属于上一轮对话仍由 AI 结合上下文判断。

原消息上的 🐳 表示“小栖已决定处理这条消息”，不代表回复或纪要已完成。获准交互成员 @ 小栖时直接通过决策并标记；未 @ 的消息在 AI 选中、接受为请求后标记，包括主动响应的记录请求。引用小栖、回答追问也在被接受后标记，不等主 Agent 完成回复。仅保存聊天或进入待判断队列不会加表情。使用 Koishi 的表情回应接口；`ACK_EMOJI_ID` 可改为 QQ 支持的表情 ID，设为空可关闭。表情发送失败会记日志，不阻塞处理。

也可以说“从全部讨论中找出对小栖的优化建议，另建一份文档”。AI 会把检索范围和整理要求交给后台，逐段读取截至这次请求本地保存的全部群成员消息，按语义保留相关建议、理由和分歧，不受近期上下文或单个话题限制。可以指定某一天、起止日期或多个话题；“今天”按北京时间的自然日计算。纪要只整理相关内容，附带的 `transcript.md` 保留检索范围内的完整原文，便于查看上下文。机器人接入前未保存的聊天不在范围内。

纪要先写核心问题、结论或未解决的阻碍，再展开方案、理由、条件和分歧；同一问题的补充放在一起，合并重复赞同，保留独立信息。普通抱怨提炼成具体问题和影响，需要区分立场或责任时保留发言人。逐字聊天放在 `transcript.md`，纪要正文不逐条复述聊天。

本地纪要保留 Markdown。普通回复和纪要在发送到 QQ 前，共用基于 [Marked](https://marked.js.org/) 的纯文本渲染器：标题显示为【标题】，强调显示为「重点」，列表、引用和表格转换为适合聊天阅读的格式，代码和外部链接保留。纪要按行分段发送，单行过长时再拆开。原文页脚只留在本地，不向群里发送 `transcript.md` 链接，也不自动补“请前往管理面板查看”。

长记录先分批提取，再合并批次之间相关的观点。提取和合并都按输入预算分批，草稿随提取进度写入；已有段落会复用，原文或选材要求变化后才重新提取。合并遇到输入或输出超限时拆小批次继续；拆到单段后直接保留已生成的正文，不因最后合并被截断而反复重跑整份记录。

对话、记录请求识别、话题识别、纪要整理和附件处理各自运行。普通回复与纪要发送也使用独立队列。主 Agent 直接写出带人设的答复，调用 `reply` 发送后结束，不再额外调用模型改写或收尾。发送队列只负责发送，不调用 AI。

AI 的结构化回复先按标准 JSON 解析，失败时用 [jsonrepair](https://github.com/josdejong/jsonrepair) 修复常见语法错误，再通过 TypeBox 校验。修复会写入日志；缺少必填字段或字段类型错误仍会报错。模型因输出上限被截断时，仍按未完成处理。

使用 DeepSeek 官方接口时，分段整理、按主题选材和合并纪要通过 SDK 启用 `high` 思考；普通对话、话题识别、保存通知和图片识别关闭思考。思考任务单独使用 `AI_THINKING_MAX_OUTPUT_TOKENS`（默认 32768）和 `AI_THINKING_TIMEOUT_MS`（默认 300000，即 5 分钟）；其他任务沿用 `AI_MAX_OUTPUT_TOKENS` 和 `AI_TIMEOUT_MS`。其他提供商继续使用服务自身的思考设置。

输出 token 上限包含思考内容、正文和工具参数，不是 QQ 回复字数限制。请求日志显示思考档位、输出上限和超时，返回日志分别显示正文字符数、思考字符数、工具名称及参数字符数，便于定位截断原因。纪要超出输出上限时，继续按现有逻辑拆小批次处理。

AI 只有调用 `reply` 才能向群里说话；会话中的普通文本和分析不会转发。直接与它交流时可以回应，但不主动延长闲聊。选范围、调用工具、决定是否发送等内部过程不应播报。

问“今天 AI 用了多少 token”可查本群按提供商、配置项、模型和用途汇总的用量。每轮调用及缓存用量保存在本地 `usage` 表，配置项名称用于区分 key，不保存 key 本身。没有上报用量的调用单独计数，不能视为零费用；金额以提供商账单为准。

排查问题时设 `LOG_LEVEL=debug`，查看 `docker compose logs -f --no-log-prefix yanqi`。任务、群号、请求消息编号和 AI 调用编号会关联模型请求、工具调用与结果；每轮还会记录用量行号、提供商、输入字符数和耗时。`LOG_DETAIL_CHARS` 控制参数、结果和异常片段的长度，默认 4000；配置中的密钥会隐藏。

`DECISION_PROVIDER` 指定未 @ 消息的入口决策模型。同一批消息共用上下文，逐条判断是否明确要求记录，或提到了群聊记录事务。分类为 `related` 时交给主 Agent，`unrelated` 时直接结束；置信度只记录在日志中，不再用额外阈值否决模型的分类。选择独立服务后不会自动回退到普通模型，调用失败由任务日志报告。只有明确设置 `DECISION_PROVIDER=llm` 才使用 `AI_MODEL` 做入口判断。@ 请求直接通过决策并标记 🐳。

话题识别、主 Agent、纪要整理和保存通知统一使用 `AI_MODEL`。自动话题识别判断哪些原文值得归档，与用户的记录请求分开运行。

`AUTO_REPLY=true` 时，获准交互成员的新消息收集一秒后进入记录相关性判断，实际启动还受 `WORK_INTERVAL_MS` 轮询和排队影响。入口按语义识别记录、纪要、转写以及查询、修改、发送已有记录等事务，不匹配固定称呼或关键词。普通闲聊、技术讨论本身或代码中的日志、数据库记录不会因此唤起主 Agent。入口只判断相关性，是否需要操作、请求对象和记录范围由主 Agent 结合完整上下文确定；提到记录不等于授权新建纪要。暂停自动归档、话题识别失败都不会阻塞这个入口；失败或重启后不重放旧请求。设为 `false` 可关闭未 @ 消息的识别，@、引用和追问后的回答继续有效。

主 Agent 收到“帮我记一下”后，先判断用户指的是哪段讨论。近期上下文不足时，调用 `read(action=context)` 向前翻聊天，找到讨论开头和结束处，再用消息起止 ID 指定完整范围；长消息的完整原文可用 `read(action=history)` 读取。不会把当前看到的片段当作全部讨论，也不默认缩成最近五分钟。范围确定后，后台处理原文、附件转写和摘要；只要求整理已有讨论时立即安排 `record`，只有需要持续记录后续发言时才使用 `follow`。

`read` 按需读取原文、纪要或记录状态；`record` 创建新文档，`edit_record` 更新、发送或暂缓已有纪要，`follow` 开始或结束连续记录。标题可由 AI 拟定，不需要用户提供话题 ID 或逐条挑选消息。后台整理仍受每日 AI 调用预算限制，额度不足时延后重试。

“把这份纪要补全为全部历史里的相关建议”会更新原文档的范围和选材要求，重新整理受影响的内容，不必另建文档。

群回复的[系统提示词](packages/bot/src/agent/prompts/common.ts)已吸收 speak-plainly 的写作原则：按问题和上下文决定篇幅，没有固定字数、句数或条数上限。简单交流简短接话，具体问题保留所需的数据、原因、条件和步骤；删除重复、无关状态、内部过程说明和套话收尾。详略由模型按语义判断，没有关键词或场景路由。原始 [skill 文件](skills/speak-plainly/SKILL.md)仅留作参考，运行时不读取或调用。这些要求优先于人设，人设只调整表达，不改变事实、权限或工具决策。纪要正文仍通过 `edit_record(action=send)` 完整发送。

[默认人设](packages/bot/src/agent/prompts/persona.ts)参考诀的认真和洛茜的俏皮，写成小栖自己的风格。管理台可以直接编辑人设提示词，保存后应用，不再读取独立的人设文件。

对话最多同时处理四个请求，同一群内同一成员的请求仍依次处理；附件最多同时处理两个。话题识别和纪要任务各自顺序执行，一份纪要中互不依赖的段落最多同时整理两段。`reply` 等待 QQ 发送结果后返回，发送不必等 Agent 完全结束。

每个附件都带有处理任务 ID。对话 Agent 可以通过 `task` 查看、等待或重试指定任务，等待后读取最新识别结果。被等待的任务优先领取；等待不会占用模型请求的超时时间。之前只下载、未识别的图片和语音，会在配置对应模型后按需解析。状态查询会返回具体任务类型、对象、进度、错误及重试时间。

刚安排整理时只能说“已开始”，不能说“记好了”。文件和数据库均保存成功后，AI 结合原讨论的时间、当前群聊和用户要求，选择发纪要、简短通知或安静保存。后台补整理旧话题默认不打扰群聊，不再把“不发全文”自动变成“发送保存通知”。需要通知时保留纪要标题。用户主动要求发送时仍可重发。同一次请求还问了其他问题，才另外调用 `reply` 回答。人设只影响发言语气，不能改变这些完成状态。

可以 @ 小栖询问记录和任务状态。后台整理、识别、附件和发送失败时，管理员可以要求“重试本群失败任务”。旧的 @ 请求不会从头重跑，避免重复开始、结束记录或改变范围；对话失败后，直接说明还要继续做什么。暂停自动整理后，仍会保存群消息并处理 @ 请求；自动任务等恢复后继续。

## 代码结构

根目录是 Nuxt 和 Naive UI 管理台：`app/` 放页面，`server/` 放接口和服务初始化。`packages/bot` 是通过 pnpm workspace 引用的机器人库。Nitro 启动时创建一个 `Yanqi` 实例，WebUI 通过 `start()`、`stop()` 和 `configure()` 管理它。停止处理时撤掉消息监听并取消 AI 请求，NapCat 连接和数据库继续可供管理台读取。下面的模块路径相对于 `packages/bot/src`。

外部依赖版本统一定义在根目录 `pnpm-workspace.yaml` 的 `catalog` 中，各包使用 `catalog:` 引用；本地机器人库使用 `workspace:*`。

| 模块                                          | 职责                                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------------- |
| `secretary.ts`                                | 收消息、保存，安排待处理的讨论                                                      |
| `onebot/`                                     | QQ 消息转换、发送和表情回应；`outbox.ts` 只消费发送队列                             |
| `tasks/worker.ts`                             | 领取任务、控制并发、执行和处理失败重试                                              |
| `agent/requests.ts`                           | 准备当前请求的上下文和工具                                                          |
| `agent/tools/`                                | 9 个工具入口；统一检查请求是否撤回，各工具只处理当前群的数据                        |
| `agent/decisions/`                            | LLM、OpenAI/Vercel、JEV、Clef 的决策实现；入口统一处理选择、用量和错误日志          |
| `agent/dialog.ts`、`recording.ts`、`media.ts` | 分别处理主对话、讨论整理与发布、媒体理解；共用 `runtime.ts` 的模型调用              |
| `recording/`                                  | 选原文、分段整理、写入纪要和决定是否发布                                            |
| `storage/`                                    | 按消息、话题、记录、纪要、附件、记忆、用量和队列存取 SQLite；`Store` 只组装这些对象 |

对话调用记录工具后拿到具体任务 ID，可以用 `task` 等待结果。后台整理先写草稿，再保存完整版本，最后决定发布。发送全文直接读数据库。需要判断是否发布时，`AI_MODEL` 在同一次调用中决定发全文、通知或安静保存，并生成所需的通知文案；不再另调模型改写。人设只用于普通回复和保存通知，不能改变发送决定。数据库和 Markdown 的格式没有改变。

决策提供者分别放在 `agent/decisions/llm.ts`、`openai.ts`、`jev.ts` 和 `clef.ts`。OpenAI 与 Vercel 共用 SDK 协议实现，Clef 复用 JEV 请求格式并解析 Workers AI 的响应封装。独立服务负责未 @ 消息的入口判断，未启用时直接使用 `AI_MODEL`。

## 管理台

管理台采用 Nuxt + Naive UI，页面和管理接口由同一个 Nitro 服务提供。服务端通过 `@yanqi/bot` 直接调用机器人。

- **启停**：顶部按钮控制消息处理与 AI 任务。停止后 NapCat 仍保持连接，可查群成员、查看和编辑记录。重新启动会继续未完成的后台任务，旧对话不会重放。
- **群与成员**：从 NapCat 同步群列表和群成员，按群启用消息记录、自动归档，勾选额外授权成员。群主、QQ 群管理员和全局名单自动获准。
- **纪要**：搜索、阅读 Markdown、查看完整原文、切换历史版本、编辑并保存新版、导出、重新整理、发送到群。删除纪要前需停止机器人；删除不影响原始消息。
- **原始消息**：按群搜索聊天，查看撤回状态、图片和语音的识别结果，下载附件、重试解析。
- **后台任务**：查看处理对象、进度、错误和发送状态，重试失败任务、取消排队任务。停止机器人可中断当前 AI 请求。
- **记忆与用量**：查看和编辑每个群的成员记忆；按日期、模型和用途查看 token。提供商未上报的用量单独标记。
- **运行日志**：查看最近 1000 条日志，按等级和内容筛选，暂停刷新、导出。完整历史仍由容器日志保留。
- **设置**：编辑连接、主模型、视觉、语音、决策提供商、人设、额度与超时。设置后端启动时是否自动运行机器人。

管理台发起的整理默认只保存，点击“发送到群”才会发送。群聊内发起的记录仍遵循原有发布决定。

配置与登录信息保存在 `DATA_DIR/management.sqlite`；群记录仍使用 `DATA_DIR/yanqi.sqlite`。首次启动导入已有 `.env`，之后由管理台保存的配置生效。修改模型或群权限不再需要改 `.env`。API 不返回已保存的密钥，输入框留空保留原值；更换模型服务地址时需要填写对应密钥。

以下参数仍由部署环境管理：`DATA_DIR`、`NITRO_HOST`、`NITRO_PORT`、`WEB_ORIGIN`、Compose 端口、时区、日志颜色，以及 NapCat 容器的 QQ 登录参数。管理台的 OneBot Token 用于连接已有 NapCat，不会替你修改 NapCat 服务端的 Token。

## 用 Docker 启动

安装 Docker 和 Docker Compose。已有 `.env` 可直接使用；没有时复制示例：

```sh
cp .env.example .env
```

填写 `BOT_QQ` 和较长的随机 `ONEBOT_TOKEN`。这两个参数也用于配置 NapCat。模型和记录群可以稍后在页面填写。然后启动言栖和 NapCat 两个服务：

```sh
docker compose up -d --build
docker compose logs yanqi
```

打开 [言栖管理台](http://127.0.0.1:3210)。首次登录填写后端日志中的安装码，并设置管理密码。然后：

1. 在 [NapCat 管理页](http://127.0.0.1:6099/webui) 完成 QQ 登录；登录 Token 从 `docker compose logs napcat` 获取。
2. 在言栖“设置”中检查连接，填写主模型；视觉、语音可分别使用其他提供商。
3. 在“群与成员”同步群列表，启用需要记录的群，选择可交互的成员。
4. 点击“启动机器人”。需要重启服务后自动运行时，在设置中打开自动启动。

页面与 `/api` 共用管理台端口，NapCat WebSocket 只在容器网络内使用。默认只向本机开放管理台 `3210` 和 NapCat `6099`。需要更改管理台端口时设置 `WEB_PORT`；部署到反向代理后时，填写 `WEB_ORIGIN=https://你的域名`，用于来源校验及 HTTPS 会话 Cookie。

Compose 将言栖的初始 OneBot 地址设为 `ws://napcat:3001`。两边初始共用 `ONEBOT_TOKEN`，NapCat 消息格式设为 `array`。管理台保存的连接设置会在后续启动时继续使用。切换 QQ 账号时，需要同时在 NapCat 登录该账号，并更新言栖中的 QQ 号。

可在 `.env` 中填写 `NAPCAT_QUICK_PASSWORD_MD5`，使用 QQ 密码的 32 位 MD5 尝试自动登录。NapCat 优先使用保存的登录状态；需要验证码或新设备验证时仍在 NapCat 页面完成。WebUI 登录 Token 与 OneBot Token 是两种凭据。参见 [NapCat 登录说明](https://github.com/NapNeko/NapCat-Docker#登录)。

如果希望从 `.env` 导入模型，每项使用 `BASE_URL,API_KEY,MODEL`，逗号之间不加空格：

```dotenv
AI_MODEL=https://text.example/v1,text-api-key,text-model
AI_VISION_MODEL=https://vision.example/v1,vision-api-key,vision-model
AI_AUDIO_MODEL=https://audio.example/v1,audio-api-key,audio-model
```

视觉服务需要支持图片输入，语音服务需要支持 OpenAI 兼容的 `/audio/transcriptions`。留空时仍保存附件原件。

## 决策提供商

设置页提供主模型、Clef、OpenAI、Vercel、JEV 卡片。选择主模型时使用 `AI_MODEL`；独立服务失败不会回退到普通 LLM。

[Cloudflare Clef](https://developers.cloudflare.com/workers-ai/models/clef/) 配置：

| 字段           | 填写内容                                                                              |
| -------------- | ------------------------------------------------------------------------------------- |
| 完整 POST 地址 | `https://api.cloudflare.com/client/v4/accounts/你的账户ID/ai/run/@cf/cloudflare/clef` |
| 模型           | `clef`                                                                                |
| API Key        | Workers AI API Token 原文，不加 `Bearer`                                              |

在 Cloudflare 控制台 **Workers AI → Use REST API** 创建 API Token、获取 Account ID。权限设置见 [官方 REST API 说明](https://developers.cloudflare.com/workers-ai/get-started/rest-api/)。

OpenAI 与 Vercel 填 SDK Base URL、密钥和模型；JEV 填完整 POST 地址。各协议实现位于 `packages/bot/src/agent/decisions/`。

## 本地开发

使用根目录 `packageManager` 指定的 pnpm 和支持的 Node.js 版本：

```sh
npx get-pnpm
pnpm install
pnpm dev
```

打开 `http://127.0.0.1:3000`。页面和接口随 Nuxt 一起启动，读取根目录 `.env`；相对 `DATA_DIR` 也按仓库根目录解析。

```sh
pnpm lint:fix
pnpm check
pnpm build
```

`pnpm build` 生成完整的 Nuxt 服务，`pnpm start` 读取根目录 `.env` 并启动 `.output/server/index.mjs`，同时提供页面和接口。`NITRO_HOST` 和 `NITRO_PORT` 控制生产服务的监听地址。

机器人统一由 WebUI 启停，也可在设置中开启服务启动后自动运行。

## 日志

管理台可以切换 `info` / `debug` 和日志详情长度。终端查看：

```sh
docker compose --ansi always logs -f --no-log-prefix yanqi
```

沿用 Koishi logger，按毫秒时间、模块名和等级排列。Compose 通过 `FORCE_COLOR=2` 打开彩色日志，默认 `TZ=Asia/Shanghai`；设 `FORCE_COLOR=0` 可关闭颜色。

`info` 记录任务、模型请求、工具调用和发送结果。`debug` 增加参数、结果片段和异常堆栈，可能包含聊天正文；`LOG_DETAIL_CHARS` 控制每段长度。AI 密钥、决策密钥和 OneBot Token 会隐藏，不记录完整请求头或图片 base64。
